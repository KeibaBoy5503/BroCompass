# BroCompass

운동·식단 블럭 노트 & 매크로 계산기. 테크니컬 블랙 UI + 네온 그린 포인트.

현재 구현 범위는 **Phase 1** (TDEE/매크로 계산 API + 대시보드)과 **Phase 2** (블럭식 데일리 노트), **Phase 3** (식단 사진 분석), **Phase 4** (논문 기반 코치)입니다. `db/schema.sql`에 플랜/실제 수행 분리 스키마가 있습니다.

## 데일리 노트 (`/note`)

한 줄 입력이 블럭으로 바뀝니다.

| 입력 | 결과 |
| --- | --- |
| `벤치프레스 5x5 80` | 운동 블럭: 5세트 × 5회, 80kg |
| `풀업 4x10` | 운동 블럭 (맨몸) |
| `닭가슴살 200kcal p40` | 식단 블럭: 200kcal, 단백질 40g |
| `현미밥 300kcal p6 c65 f2` | 식단 블럭: 탄수 65g, 지방 2g |
| 그 외 | 메모 블럭 |

- 세트 버튼을 누르면 완료(Actual) 처리되고 스프링 애니메이션과 진동이 나옵니다. 마지막 세트는 더 강한 패턴입니다.
- 세트를 완료하면 직전 세트의 실제값(없으면 플랜 값)이 기록되고, `▼ 실제 기록 수정`을 열어 세트별 중량(±2.5kg)과 횟수(±1)를 고칠 수 있습니다. 플랜과 다른 세트에는 노란 점이 붙고, 볼륨은 실제값으로 계산됩니다.
- 상단 날짜 바에서 전날/다음날 이동, 날짜 탭으로 달력 선택, `오늘` 버튼으로 복귀합니다. 날짜별로 따로 저장됩니다.
- 왼쪽 `⋮⋮` 핸들을 끌어 순서를 바꿉니다 (dnd-kit).
- 상단 PLAN vs ACTUAL 바에서 세트·볼륨·칼로리·단백질 달성률을 봅니다.
- `⧉ 이전 계획 복사`: 가장 가까운 이전 기록(최대 14일 전)의 계획을 오늘로 복사합니다. 세트 완료·섭취 체크와 실제 기록은 비우고 계획만 가져오며, 이미 있는 블럭 뒤에 추가됩니다. 이 기기와 서버를 모두 찾아서 다른 기기에서 쓴 기록도 복사됩니다.

### 서버 저장 (로컬 우선)

- 변경 사항은 즉시 브라우저 `localStorage`에 저장되고, 0.8초 뒤 서버(`PUT /api/notes/{date}`)로 올라갑니다. 서버가 꺼져 있어도 그대로 쓸 수 있고, 상단에 `오프라인 · 이 기기에만 저장`으로 표시됩니다. 다음에 서버가 켜진 상태로 그 날짜를 열면 다시 올라갑니다.
- 충돌 규칙은 **마지막 수정 시각(updatedAt)이 더 최신인 쪽이 이김**입니다. 기기 시계가 크게 어긋나 있으면 오래된 쪽이 이길 수 있습니다.
- 저장소는 SQLite(`backend/brocompass.db`, 경로는 `BROCOMPASS_DB`로 변경)이고, 날짜별 JSON 문서 한 건으로 저장합니다. 정규화된 `db/schema.sql`(plan_blocks / actual_logs)은 Supabase로 옮길 때의 목표 구조이며, `backend/store.py`의 `NoteStore`와 같은 메서드를 구현하면 교체할 수 있습니다.
- **아직 인증이 없습니다.** 개인 PC/로컬용이며, 인터넷에 공개하기 전에는 사용자 인증을 붙여야 합니다.

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| GET | `/api/notes/{date}` | 노트 조회 (없으면 404) |
| PUT | `/api/notes/{date}` | 저장. 서버에 더 최신 노트가 있으면 저장하지 않고 그 노트를 반환 |
| GET | `/api/notes?start=&end=` | 기간 내 블럭이 있는 날짜 목록 |

## 구조

```

```

## 실행

백엔드:

```bash
cd backend
pip install -r requirements.txt
uvicorn main:app --reload --port 8000
pytest            # 계산 로직 테스트
```

프론트엔드 (모바일 폭 390px 기준으로 먼저 확인하세요):

```bash
cd frontend
npm install
npm run dev       # http://localhost:3000
```

`/api/*` 요청은 `next.config.js`의 rewrite로 FastAPI(`API_URL`, 기본 `http://localhost:8000`)에 전달됩니다.

## 계산 방식

- BMR: Mifflin-St Jeor (체지방률 입력 시 Katch-McArdle)
- TDEE = BMR × 활동계수 (1.2 ~ 1.9)
- 목표 칼로리: 감량 -20% / 유지 / 증량 +10%
- 매크로: 체질별 탄단지 비율, 단백질은 최소 1.6g/kg 보장

계산 결과는 일반적인 추정치이며 의료적 조언이 아닙니다.

## 식단 사진 분석 (Phase 3)

데일리 노트의 `📷 사진으로 식단 추가`로 음식 사진을 고르면, 서버가 Vision AI에 보내 음식별 칼로리·탄단지를 추정하고, 검토 화면에서 값을 고친 뒤 식단 블럭으로 추가합니다. (`POST /api/meal/analyze`)

**설정** — 기본은 NVIDIA build.nvidia.com 무료 API입니다 (`backend/.env.example` 참고). 무료 모델은 예고 없이 종료되므로(`HTTP 410`/`404`), 오류 메시지가 나오면 `https://integrate.api.nvidia.com/v1/models`(키 필요)에서 현재 모델을 확인해 `VISION_MODEL`/`COACH_MODEL`을 바꾸세요.

```bash
export NVIDIA_API_KEY=nvapi-...       # build.nvidia.com → Settings → API Keys
# export VISION_MODEL=...             # 404/410 이 나면 이미지 입력 가능한 모델 ID로 변경
uvicorn main:app --reload --port 8000
```

OpenAI를 쓰려면 `VISION_API_KEY`, `VISION_BASE_URL=https://api.openai.com/v1`, `VISION_MODEL=gpt-4o`를 설정합니다. API 키는 서버에만 있고 브라우저로 나가지 않습니다.

**알아둘 점**

- 무료 API는 분당 약 40회 제한이 있고, 총 크레딧·약관은 NVIDIA 쪽 정책을 따릅니다. 개인 개발·테스트용으로 쓰세요. 서버도 분당 30회(`VISION_RPM`)로 먼저 막습니다.
- 사진 한 장으로 추정한 영양값은 오차가 큽니다. 그래서 항상 검토·수정 단계를 거치고, 칼로리와 탄단지가 서로 안 맞으면 경고를 표시합니다.
- 사진은 업로드 전에 브라우저에서 긴 변 768px, 약 150KB 이하로 줄여 보냅니다. 서버에는 사진을 저장하지 않습니다.
- 무료 호스팅 모델 목록과 입력 형식은 바뀔 수 있습니다. 모델이 JSON 형식을 어기면 한 번 더 묻고, 그래도 실패하면 오류를 보여줍니다.
- 인증이 없어서 서버 주소를 아는 사람은 누구나 분석을 요청할 수 있습니다. 공개 배포 전에 인증을 붙이세요.

## 논문 기반 코치 (Phase 4, RAG)

`/coach` 화면에서 최근 7/14/28일 기록을 분석해 약점을 찾고, PubMed 논문을 근거로 붙여 보여줍니다.

**동작 순서**

1. **기록 분석** (`insights.py`, 규칙 기반): 주간 부위별 세트 수, 밀기/당기기 균형, 단백질(체중 입력 시), 같은 운동의 정체기, 어깨·무릎·허리 불편 메모, 격투기/유산소 병행을 찾습니다.
2. **논문 검색** (`retrieval.py`): 발견 사항마다 영어 검색 질의(`topics.py`)로 논문 DB를 검색합니다. BM25 키워드 검색이고, 질의 단어의 60% 이상이 논문에 없으면 후보에서 뺍니다. 관련 논문이 없으면 억지로 인용하지 않습니다.
3. **AI 요약** (`coach.py`, 선택): 발견 사항과 논문 발췌만 LLM에 보내 한국어 요약과 플랜 조정 제안을 받습니다. LLM이 인용한 PMID가 실제로 검색된 논문이 아니면 그 조언은 버립니다. 메모 원문은 보내지 않습니다.
4. 부족한 근육군에는 `오늘 노트에 추가` 버튼으로 운동 블럭을 바로 넣을 수 있습니다 (중량은 0으로 들어가니 노트에서 실제 값을 기록하세요).

**처음 한 번: 논문 DB 채우기** (내 PC에서, 인터넷 필요)

```bash
cd backend
python ingest_pubmed.py --email you@example.com          # 토픽당 30편, 메타분석/체계적 문헌고찰/RCT/리뷰 위주
python ingest_pubmed.py --topics volume,protein --per-topic 50
python ingest_pubmed.py --embed                          # (선택) 임베딩도 생성, EMBED_MODEL 필요
```

- 논문 데이터는 앱에 들어 있지 않고 PubMed 공식 API(E-utilities)에서 직접 받습니다. 다시 실행해도 안전합니다.
- NCBI 이용 규칙(키 없이 초당 3회)을 지키도록 요청 사이에 간격을 둡니다. 대량 수집은 미국 동부 기준 주말/야간을 권장합니다.
- 수집 결과가 0편인 토픽은 PubMed 검색식(`topics.py`의 `pubmed_term`)이 너무 좁은 것이니 고쳐서 다시 실행하세요.
- 임베딩(`--embed`)은 실험적 기능입니다. 키워드 검색이 후보를 정하고 임베딩은 순서만 다듬습니다.

**알아둘 점**

- 추천은 **참고용**입니다. 기준값(주 10세트, 1.6g/kg 등)은 널리 쓰이는 경험칙(휴리스틱)이며 개인 처방이 아닙니다. 통증이 있으면 전문가와 상담하세요.
- AI 요약은 논문 초록을 바탕으로 하지만 틀릴 수 있습니다. 화면의 논문 링크와 발췌를 직접 확인하세요.
- 분석은 이 기기(브라우저)에 저장된 기록만 사용합니다. 다른 기기에서 쓴 기록은 포함되지 않습니다.
- 서버 API(`/api/coach/recommend`, `/api/papers/stats`)도 인증이 없습니다. 공개 배포 전에 인증을 붙이세요.

## 정확도 개선 (Phase 4.5)

**논문 연결**
- 토픽마다 **필수 용어**(예: 후면삼각근 → `deltoid`, 격투기 → 격투기 종목 이름)와 **제외 집단**(제목에 뇌졸중·코로나·암 등)을 두어, 키워드만 겹치는 엉뚱한 논문을 후보에서 뺍니다 (`topics.py`).
- AI 요약을 켠 경우, 모델이 제목·발췌를 보고 "이 발견 사항과 상관없다"고 표시한 논문은 숨기고 몇 편을 숨겼는지 알려줍니다. 숨긴 논문은 AI 요약의 인용으로도 인정하지 않습니다.
- 후면삼각근·밀기/당기기·격투기 검색식을 넓혔으니 **`python ingest_pubmed.py`를 다시 실행**하세요 (이미 받은 논문은 건너뜁니다).
- 점검 도구: `python eval_retrieval.py` — 추천 항목마다 어떤 논문이 붙는지 출력합니다 (네트워크·키 불필요). 결과를 공유하면 기준을 더 조정할 수 있어요.

**사진 분석**
- 모델에게 제공량(g)과 확신도를 같이 묻고, 칼로리가 탄단지(4/4/9)와 25% 넘게 다르면 두 수치를 함께 보여 줍니다.
- 검토 화면에서 항목별 **양 조절(0.5×~2×)**로 칼로리·탄단지를 한 번에 바꾸고, 어긋난 칼로리는 탄단지 기준으로 맞출 수 있습니다.
- 음식을 잘못 알아봤다면 **힌트**(예: "닭가슴살 샐러드")를 적어 같은 사진을 다시 분석합니다. 힌트는 음식 이름 참고용으로만 전달됩니다.

## 화면 구성과 게임 피드백 (Phase 5)

- **PC 화면**: 넓은 화면(lg 이상)에서는 왼쪽 사이드바, 좁은 화면에서는 아래 탭바로 이동합니다. 노트 화면은 PC에서 2단(기록 | 요약·게임 패널)이 됩니다.
- **신기록**: 같은 이름의 운동끼리 비교합니다. 중량 운동은 추정 1RM(Epley, 횟수는 12회까지만 반영), 맨몸 운동은 횟수 기준입니다. 그 운동의 첫 기록은 신기록으로 세지 않습니다. 새 신기록이 생기면 알림과 진동이 나옵니다.
- **연속 운동일**: 완료한 세트가 있는 날을 이어서 셉니다. 오늘 운동 전이면 어제까지의 연속을 유지해서 보여줍니다.
- **주간 퀘스트**(최근 7일): 3일 운동, 30세트, 식단 계획 90% 이상 지킨 날 3일, 신기록 1회.
- **레벨**: XP = 완료 세트 1점 + 운동한 날 10점 + 신기록 25점. 레벨 L에 필요한 누적 XP는 50×(L-1)².
- **근육 맵**: 최근 7일 근육군별 완료 세트 수를 색으로 보여줍니다(0세트 회색, 1~9 노랑, 10 이상 초록). 분류 규칙은 `backend/insights.py`와 같고, 한쪽을 고치면 `frontend/lib/muscles.ts`도 맞춰야 합니다.
- 게임 통계는 이 기기(localStorage)에 저장된 노트 기준입니다.

## 격투기 세션과 다이어트 도우미 (Phase 6)

- **세션 블럭**: `스파링 60분 rpe7`처럼 적으면 시간 기반 훈련 블럭이 됩니다. 부하 = 분 × RPE (AU)이고 완료한 세션만 셉니다. 코치는 최근 7일 부하가 직전 7일의 1.5배를 넘거나(직전 부하 300 AU 이상일 때), RPE 8 이상 세션이 3일 이상이면 알려줍니다. 두 기준은 휴리스틱입니다.
- **다이어트 도우미(`/diet`)**: 현재·목표 체지방률, 체중, 유지 칼로리, 주당 감량 속도(체중 대비 %)로 목표 체중·예상 기간·하루 섭취량·주별 체중 곡선을 계산합니다. 제지방량이 그대로라고 가정하고 체지방 1kg을 7,700kcal로 봅니다. 몸 모형은 체지방률 5~40%를 높이로 나타낸 게이지입니다.

## 다국어 UI (한국어 · 日本語 · English)

- 사이드바(좁은 화면에서는 화면 오른쪽 위)의 언어 버튼으로 전환하고, 선택은 이 기기에 저장됩니다. 저장된 값이 없으면 브라우저 언어(ja/en)를 따릅니다.
- 번역 사전은 `frontend/lib/messages.ts` 한 곳입니다. 키는 한국어 원문이고, 코드에서는 `t("오늘")`처럼 씁니다. 사전에 없는 문장은 한국어 그대로 보이므로 번역이 빠져도 화면은 깨지지 않습니다. `{n}` 같은 자리표시자는 `t("{n}세트", { n: 3 })`처럼 채웁니다.
- 번역된 화면: 내비게이션, 계산기, 노트(블럭·요약·게임 패널·근육 맵), 다이어트 도우미, 코치 화면의 틀, 사진 분석 화면. 서버가 만드는 문장(코치 인사이트, 추천 운동 이름, 면책 문구, 사진 분석 경고)은 요청의 `lang`(ko/ja/en)에 맞춰 `backend/texts.py`의 문구표로 만들어지고, AI 요약과 사진 분석 메모는 프롬프트에 출력 언어를 지정해 받습니다. 서버 오류 메시지(HTTP 상세)와 논문 원문은 번역하지 않습니다. 언어를 바꾼 뒤에는 코치 화면에서 다시 분석해야 새 언어로 나옵니다.
- 운동 이름은 한국어·일본어·영어 어느 쪽으로 입력해도 근육군을 인식합니다.

## 공개 배포 시 보호 장치 (4차 패치)

로그인이 없는 대신 아래 장치로 데모를 보호합니다. 정식 인증이 아니므로 "공개 데모용 안전장치" 수준입니다.

- **사용자별 노트 분리:** 브라우저가 만든 무작위 ID(`X-Client-Id`)로 노트를 나눕니다. 서버에서 `REQUIRE_CLIENT_ID=1`을 켜면 ID 없는 요청을 거절합니다. 기존 서버 노트(ID 도입 이전)는 공개 모드에서 보이지 않으며, 브라우저의 로컬 기록은 그대로 남아 새 ID 로 다시 동기화됩니다.
- **IP 별 요청 제한:** 사진 분석·코치·노트 저장에 각각 분당 한도를 둡니다(`IP_VISION_RPM` 등).
- **하루 AI 호출 총량:** `AI_DAILY_CAP`(UTC 기준)으로 외부 AI 키의 한도 소진을 막습니다.
- **저장 한도:** 한 사용자가 저장할 수 있는 노트 수를 1,000건으로 제한합니다.
- **한계:** 제한 상태는 서버 메모리에 있어 재시작하면 초기화되고, 서버를 여러 대로 늘리면 각각 따로 계산됩니다.
