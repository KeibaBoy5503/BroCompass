## ✨ 特長

- 📝 **1行がブロックになる:** `ベンチプレス 5x5 80` と入力すると、計画と実績を比べられる運動ブロックに変わります
- 💾 **ローカルファースト同期:** オフラインでも使え、後でサーバーに同期します（新しい編集が勝ち）

- 🧠 **論文に基づくコーチ:** 記録から弱点を見つけ、PubMed論文を根拠として添えます（根拠がなければ「根拠なし」と表示）

ブロック形式の運動・食事ノートアプリです。マクロ計算機、食事写真のAI分析、PubMed論文を根拠にしたコーチ機能を備えています。

実装済みの範囲: **Phase 1**（TDEE/マクロ計算API + ダッシュボード）、**Phase 2**（ブロック形式のデイリーノート）、**Phase 3**（食事写真の分析）、**Phase 4**（論文に基づくコーチ）、**Phase 5**（PCレイアウト、ゲーム的フィードバック）、**Phase 6**（格闘技セッション、ダイエットヘルパー）、韓国語・日本語・英語のUI。`db/schema.sql` に、計画と実績を分離した目標スキーマがあります。

## 📝 デイリーノート (`/note`)

1行の入力がブロックに変わります。

| 入力 | 結果 |
| --- | --- |
| `ベンチプレス 5x5 80` | 運動ブロック: 5セット × 5回、80kg |
| `懸垂 4x10` | 運動ブロック（自重） |
| `鶏胸肉 200kcal p40` | 食事ブロック: 200kcal、タンパク質40g |
| `玄米 300kcal p6 c65 f2` | 食事ブロック: 炭水化物65g、脂質2g |
| それ以外 | メモブロック |

種目名は韓国語・日本語・英語のどれで入力しても認識され、長めの種目名の軽い入力ミスは許容されます。

- セットのボタンを押すと完了（実績）になり、スプリングアニメーションと振動が出ます。最後のセットはより強いパターンです。
- セットを完了すると、直前セットの実績値（なければ計画値）が記録されます。`▼ 実績を修正` を開くと、セットごとの重量（±2.5kg）と回数（±1）を直せます。計画と異なるセットには黄色い点が付き、ボリュームは実績値で計算されます。
- 上部の日付バーで前日/翌日に移動し、日付タブでカレンダーを選び、`今日` ボタンで戻ります。ノートは日付ごとに保存されます。
- 左の `⋮⋮` ハンドルをドラッグして順序を変更します (dnd-kit)。
- 上部の PLAN vs ACTUAL バーで、セット・ボリューム・カロリー・タンパク質の達成率を確認できます。
- `⧉ 前回の計画をコピー`: 直近の過去の記録（最大14日前まで）の計画を今日にコピーします。セット完了・摂取チェック・実績は空にして計画だけを持ち込み、既存のブロックの後ろに追加されます。この端末とサーバーの両方を探すので、別の端末で書いた記録もコピーできます。

### 💾 サーバー保存（ローカルファースト）

- 変更はすぐブラウザの `localStorage` に保存され、0.8秒後にサーバー（`PUT /api/notes/{date}`）へ送られます。サーバーが止まっていてもそのまま使え、画面上部に `オフライン・この端末のみ保存` と表示されます。次にサーバーが起動している状態でその日付を開くと、再度アップロードされます。
- 競合時のルール: **更新時刻 (`updatedAt`) が新しい方が勝ちます。** 端末の時計が大きくずれていると、古い方が勝つ場合があります。
- 保存先は SQLite（`backend/brocompass.db`、パスは `BROCOMPASS_DB` で変更）で、日付ごとに1件のJSONドキュメントとして保存します。正規化した `db/schema.sql`（plan_blocks / actual_logs）は将来の Supabase 移行時の目標構造です。`backend/store.py` の `NoteStore` と同じメソッドを実装すれば置き換えられます。
- **ログイン機能はありません。** ブラウザごとの無作為なID（`X-Client-Id`）でノートを分離します。詳細は下の「公開デモの保護機能」を参照してください。これは正式な認証ではありません。

| メソッド | パス | 説明 |
| --- | --- | --- |
| GET | `/api/notes/{date}` | ノート取得（なければ404） |
| PUT | `/api/notes/{date}` | 保存。サーバーに新しいノートがあれば保存せず、そのノートを返す |
| GET | `/api/notes?start=&end=` | 期間内でブロックがある日付の一覧 |

## 🧮 計算方法

- BMR: Mifflin-St Jeor（体脂肪率を入力した場合は Katch-McArdle）
- TDEE = BMR × 活動係数（1.2〜1.9）
- 目標カロリー: 減量 −20% / 維持 / 増量 +10%
- マクロ: 体型別の炭水化物・タンパク質・脂質の比率。タンパク質は最低 1.6g/kg を確保

計算結果は一般的な推定値であり、医学的助言ではありません。

## 📷 食事写真の分析（Phase 3）

デイリーノートの `📷 写真から食事を追加` で料理の写真を選ぶと、サーバーがVision AIに送り、料理ごとのカロリーとPFCを推定します。確認画面で値を直して、食事ブロックとして追加します。（`POST /api/meal/analyze`）

**設定** — 既定は NVIDIA build.nvidia.com の無料APIです（`backend/.env.example` 参照）。無料ホスティングのモデルは予告なく終了したり応答しなくなったりします（`HTTP 404`/`410`、または一覧にあるのに実際は配備されていないモデル）。エラーが出たら、診断ツールで自分のキーで使えるモデルと、実際に応答するモデルを確認してください。

```bash
cd backend
export NVIDIA_API_KEY=nvapi-...                     # build.nvidia.com → Settings → API Keys
python diagnose_models.py                           # キーで見えるモデル一覧
python diagnose_models.py --vision                  # 画像入力の候補を実際に試す
python diagnose_models.py --scan --timeout 30       # いま応答するテキストモデルを探す
export VISION_MODEL=...                             # OKが出たモデルID
export VISION_NO_THINK=1                            # 推論モデルの遅い「思考」を省略（--nothink で確認してから）
uvicorn main:app --reload --port 8000
```

OpenAIを使う場合は、`VISION_API_KEY`、`VISION_BASE_URL=https://api.openai.com/v1`、`VISION_MODEL=gpt-4o` を設定します。APIキーはサーバーだけが持ち、ブラウザには出ません。

**注意点**

- 無料APIには毎分約40回の制限があり、総クレジットや規約はNVIDIA側のポリシーに従います。個人の開発・テスト用途で使ってください。サーバー側も毎分30回（`VISION_RPM`）で先に制限します。
- 写真1枚からの栄養推定は誤差が大きいため、必ず確認・修正の手順を挟み、カロリーとPFCが合わないときは警告を表示します。
- 写真はアップロード前にブラウザで長辺768px・約150KB以下に縮小します。サーバーは写真を保存しません。
- 無料ホスティングのモデル一覧や入力形式は変わることがあります。モデルがJSON形式を守らなかった場合は1回だけ再質問し、それでも失敗したらエラーを表示します。推論モデルは「思考」中に回答が空になることがあるため、サーバーは思考テキストを代わりに使い、出力が途中で切れた場合はそう知らせます（`VISION_MAX_TOKENS` で上限を増やせます）。

## 🧠 論文に基づくコーチ（Phase 4、RAG）

`/coach` 画面で直近7/14/28日の記録を分析して弱点を見つけ、PubMedの論文を根拠として添えて表示します。

**動作の流れ**

1. **記録の分析**（`insights.py`、ルールベース）: 部位別の週間セット数、押す/引くのバランス、タンパク質（体重入力時）、同じ種目の停滞、肩・膝・腰の不調メモ、格闘技/有酸素の併用による負荷を検出します。
2. **論文検索**（`retrieval.py`）: 発見事項ごとに英語の検索クエリ（`topics.py`）で論文DBを検索します。BM25のキーワード検索で、単語の希少度（IDF）で重み付けした関連度ゲート、トピックごとの必須用語と除外集団、複数クエリの結果をRRF（Reciprocal Rank Fusion）で統合します。合わない論文は除外し、無理に引用することはありません。
3. **AI要約**（`coach.py`、任意）: 発見事項と論文の抜粋だけをLLMに送り、選択中のUI言語で要約とプラン調整の提案を受け取ります。LLMが引用したPMIDが実際に検索された論文でなければ、そのアドバイスは破棄します。メモの原文は送りません。
4. 不足している筋群には `今日のノートに追加` ボタンで運動ブロックをすぐ入れられます（重量は0で入るので、ノートで実際の値を記録してください）。

**最初の1回: 論文DBを作る**（自分のPCで、インターネットが必要）

```bash
cd backend
python ingest_pubmed.py --email you@example.com          # トピックごとに30件。メタ分析/システマティックレビュー/RCT/レビュー中心
python ingest_pubmed.py --topics volume,protein --per-topic 50
python ingest_pubmed.py --embed                          # （任意）埋め込みも生成。EMBED_MODELが必要
```

- 論文データはアプリに同梱されておらず、PubMed公式API（E-utilities）から直接取得します。再実行しても安全です。
- NCBIの利用規則（キーなしで毎秒3回）を守るため、リクエストの間隔を空けています。大量収集は米国東部時間の週末や夜間を推奨します。
- 取得結果が0件のトピックは、PubMed検索式（`topics.py` の `pubmed_term`）が狭すぎるので、直して再実行してください。
- 埋め込み（`--embed`）は実験的機能です。候補はキーワード検索が決め、埋め込みは順序の調整だけに使います。

**注意点**

- 推奨は**参考情報**です。基準値（週10セット、1.6g/kgなど）は広く使われる経験則（ヒューリスティクス）であり、個人への処方ではありません。痛みがある場合は専門家に相談してください。
- AI要約は論文の抄録に基づきますが、誤ることがあります。画面の論文リンクと抜粋を自分で確認してください。
- 分析は、このブラウザに保存された記録だけを使います。別の端末で書いた記録は含まれません。
- AIの処理が失敗・タイムアウトしても、ルールベースの分析結果と論文は表示されます。待ち時間の上限は `AI_TIMEOUT_S` で増やせます。

## 🎯 精度の改善（Phase 4.5）

**論文との結び付け**
- トピックごとに**必須用語**（例: 後部三角筋 → `deltoid`、格闘技 → 競技名）と**除外集団**（タイトルに脳卒中・COVID・がんなど）を設け、キーワードが重なるだけの無関係な論文を候補から外します（`topics.py`）。
- AI要約を有効にしている場合、モデルが「この発見事項と無関係」と判定した論文は非表示にし、何件隠したかを表示します。隠した論文は引用としても認めません。
- 後部三角筋・押す/引く・格闘技の検索式を広げたので、**`python ingest_pubmed.py` を再実行**してください（取得済みの論文はスキップされます）。
- 確認ツール: `python eval_retrieval.py` — 推奨項目ごとにどの論文が付くかを出力します（ネットワークもキーも不要）。

**写真分析**
- モデルに提供量（g）と確信度も尋ね、カロリーがPFC（4/4/9 kcal/g）から計算した値と25%を超えて違う場合は、2つの数値を並べて表示します。
- 確認画面で、品目ごとの**分量ボタン（0.5×〜2×）**でカロリーとPFCを一括で変更でき、ずれたカロリーはPFC基準で合わせられます。
- 料理を誤認識した場合は**ヒント**（例:「鶏胸肉のサラダ」）を入力して同じ写真を再解析します。ヒントは料理名の参考としてのみ渡されます。

## 🎮 画面構成とゲーム的フィードバック（Phase 5）

- **PC画面**: 広い画面（lg以上）では左のサイドバー、狭い画面では下のタブバーで移動します。ノート画面はPCで2カラム（記録 | サマリー・ゲームパネル）になります。
- **自己ベスト（PR）**: 同じ名前の種目同士で比較します。重量種目は推定1RM（Epley式、回数は12回まで反映）、自重種目は回数で比較します。その種目の最初の記録はPRに数えません。新しいPRが出ると通知と振動が出ます。
- **連続記録日**: 完了したセットがある日を連続で数えます。今日の運動前は、昨日までの連続を保って表示します。
- **週間クエスト**（直近7日）: 3日運動、30セット、食事計画を90%以上守った日が3日、PR 1回。
- **レベル**: XP = 完了セット1点 + 運動した日10点 + PR 25点。レベルLに必要な累計XPは 50×(L−1)² です。
- **筋肉マップ**: 直近7日の筋群別の完了セット数を色で表示します（0セットは灰色、1〜9は黄色、10以上は緑）。分類ルールは `backend/insights.py` と同じで、片方を直したら `frontend/lib/muscles.ts` も合わせる必要があります。
- ゲーム統計は、この端末（localStorage）に保存されたノートが基準です。

## 🥊 格闘技セッションとダイエットヘルパー（Phase 6）

- **セッションブロック**: `スパーリング 60分 rpe7` のように書くと、時間ベースのトレーニングブロックになります。負荷 = 分 × RPE（AU）で、完了したセッションだけを数えます。コーチは、直近7日の負荷が直前7日の1.5倍を超える場合（直前の負荷が300AU以上のとき）や、RPE 8以上のセッションが3日以上ある場合に知らせます。この2つの基準はヒューリスティクスです。
- **ダイエットヘルパー（`/diet`）**: 現在・目標の体脂肪率、体重、維持カロリー（計算機で保存したTDEEと連動）、週あたりの減量ペース（体重に対する%）から、目標体重・予想期間・1日の摂取量・週ごとの体重曲線を計算します。除脂肪体重が変わらないと仮定し、脂肪1kgを7,700kcalとして換算します。無理な計画（週に体重の1%超、不足がTDEEの25%超、1日1,200kcal未満、目標体脂肪率10%未満）には警告を表示します。体型モデルは、体脂肪率5〜40%を高さで表すゲージです。

## 🌏 多言語UI（한국어 · 日本語 · English）

- 言語ボタン（サイドバー、狭い画面では右上）で切り替え、選択はこの端末に保存されます。保存された値がなければ、ブラウザの言語（ja/en）に従います。
- 翻訳辞書は `frontend/lib/messages.ts` の1か所です。キーは韓国語の原文で、コードでは `t("오늘")` のように使います。辞書にない文は韓国語のまま表示されるので、翻訳が抜けても画面は壊れません。`{n}` のようなプレースホルダーは `t("{n}세트", { n: 3 })` のように埋めます。
- 翻訳済みの画面: ナビゲーション、計算機、ノート（ブロック・サマリー・ゲームパネル・筋肉マップ）、ダイエットヘルパー、コーチ画面の枠、食事写真の画面。サーバーが作る文（コーチの所見、推奨種目名、免責文、写真分析の警告）は、リクエストの `lang`（ko/ja/en）に合わせて `backend/texts.py` の文言表で生成されます。AI要約と写真分析のメモは、プロンプトで出力言語を指定して受け取ります。サーバーのエラーメッセージ（HTTPの詳細）と論文の原文は翻訳しません。言語を切り替えた後は、コーチ画面で再度分析すると新しい言語で出ます。
- 日本語・英語の文言はAIの支援で翻訳したもので、まだネイティブによるレビューを受けていません。
- 種目名は韓国語・日本語・英語のどれでも認識されます。

## 🛡️ 公開デモの保護機能

ログイン機能がないため、次の仕組みで公開デモを守ります。正式な認証ではなく、デモ向けの安全装置です。

- **ユーザーごとのノート分離:** ブラウザが作る無作為なID（`X-Client-Id`）でノートを分けます。サーバーで `REQUIRE_CLIENT_ID=1` を有効にすると、IDのないリクエストを拒否します。ID導入前のサーバー上のノートは公開モードでは見えませんが、ブラウザ内のローカル記録は残り、新しいIDで再同期されます。
- **IPごとのリクエスト制限:** 写真分析・コーチ・ノート保存にそれぞれ毎分の上限を設けます（`IP_VISION_RPM` など）。
- **1日のAI呼び出し総量:** `AI_DAILY_CAP`（UTC基準）で、外部AIキーの上限が尽きるのを防ぎます。
- **保存上限:** 1ユーザーが保存できるノートは1,000件までです。
- **制限事項:** 制限の状態はサーバーのメモリ上にあるため、再起動で初期化され、サーバーを複数台にするとそれぞれ別に数えられます。
